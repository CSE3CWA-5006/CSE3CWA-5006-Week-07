Lab tasks: Build, Run and Trace an IoT Data Pipeline (MQTT + MongoDB + React)

In this lab you install and run a small but complete IoT system: a sensor simulator that publishes readings over MQTT, and a dashboard that subscribes, stores readings in MongoDB, and shows them live in a React page. You will then read the code to see exactly how each stage connects, and use Ubuntu tools to watch the data move through the broker and the database with your own eyes.

 

Who this lab is for

Parts 1–7 are for both CSE3CWA and CSE5006 students. Part 8 is an optional advanced extension for CSE5006 students only; CSE3CWA students may read it for interest but are not required to complete it.

 

How to apply code changes

Changed a React file (.jsx) or CSS? The Vite dev server hot-reloads it; just look at the browser. Changed the sensor or backend (a .js file)? Stop that program with Ctrl + C and start it again so Node runs the new code.

Part 1 — Install the services on Ubuntu

The system needs two background services: the Mosquitto MQTT broker and MongoDB. A script installs and starts both. You also need Node.js 20 LTS or newer (check with node --version).

  1. Unzip the project package somewhere easy to find, and open a terminal in that folder.
  2. Run the setup script:
chmod +x setup_ubuntu_services.sh
./setup_ubuntu_services.sh

You will be asked for your password (installing system packages needs sudo). When it finishes, Mosquitto is listening on port 1883 and MongoDB on 127.0.0.1:27017.

Part 2 — Run both programs

Use two terminals. The two programs never call each other — they meet only at the MQTT broker.

Terminal 1 — the dashboard (backend + React frontend):

cd iot_mqtt_dashboard
chmod +x run_ubuntu.sh
./run_ubuntu.sh

Then open the dashboard in your browser at http://localhost:5174. It will be empty at first — that is expected.

Terminal 2 — the sensor simulator:

cd iot_sensor_simulator
chmod +x run_ubuntu.sh
./run_ubuntu.sh

Part 3 — Visual test in the browser

With both programs running, open http://localhost:5174 and confirm the system works end to end:

  • Within a few seconds, three reading cards appear (temperature, humidity, pressure) and their values update on their own.
  • The live chart draws a smooth curve that grows over time (the values drift gently, they do not jump).
  • Use the Sensor dropdown to switch the chart between temperature, humidity and pressure.
  • Use the Time window dropdown (1 / 5 / 15 / 60 minutes) and watch how much history the chart shows.
  • The table at the bottom lists the latest reading of each sensor with its device, topic and timestamps.

Now open the backend health endpoint in the browser: http://localhost:4100/api/health. Confirm that mqttConnected and mongodbConnected are both true, and that storedMessages rises each time you refresh.

Part 4 — Read the code: connecting to MQTT and MongoDB

Now look at how the programs connect. Open the files in your editor.

4.1 — The sensor connects to MQTT. Open iot_sensor_simulator/sensor-publisher.js and find the connection. The simulator is an MQTT client; mqtt.connect opens a connection to the broker, and the connect event fires once it is ready:

const brokerUrl = process.env.MQTT_BROKER_URL || "mqtt://localhost:1883";
const client = mqtt.connect(brokerUrl, { clean: true, reconnectPeriod: 2000 });
client.on("connect", () => { console.log(`[MQTT] Connected to ${brokerUrl}`); });

4.2 — The backend connects to MongoDB. Open iot_mqtt_dashboard/server/src/server.js and find startMongo. It opens the database, selects the collection, and builds indexes:

mongoClient = new MongoClient(config.mongodbUri);   // mongodb://127.0.0.1:27017
await mongoClient.connect();
readings = mongoClient.db(config.mongodbDb)          // week7_iot
  .collection(config.mongodbCollection);             // sensor_readings
await readings.createIndex({ receivedAt: -1 });

4.3 — The backend also connects to MQTT. In the same file, startMqtt connects to the same broker as the sensor. This is the key idea: both programs are MQTT clients of one broker.

Part 5 — Read the code: subscribe vs publish

5.1 — The sensor publishes. In sensor-publisher.js, each sensor builds its topic from the base topic plus the sensor type, then calls client.publish:

const topic = `${baseTopic}/${sensor.sensorType}`;   // e.g. .../temperature
client.publish(topic, JSON.stringify(payload), { qos });

5.2 — The backend subscribes. In server.js, startMqtt subscribes to a wildcard topic filter that matches every sensor:

mqttClient.subscribe(config.mqttSubscribeTopic, { qos: 1 });
// MQTT_SUBSCRIBE_TOPIC = latrobe/+/+/+/+

The sensor publishes to a 5-level topic such as latrobe/building-a/level-2/room-204/temperature. The subscription has five + levels, so it matches every sensor in every room. Publish sends one message to one topic; subscribe registers interest in a pattern of topics.

Part 6 — Read the code: packet → MongoDB → UI

6.1 — The backend takes the packet out of MQTT and stores it. When a message arrives, the message event gives the backend the topic and the payload. It parses, normalises, validates, then inserts into MongoDB:

mqttClient.on("message", async (topic, message) => {
  const payload = parseJsonPayload(message);          // text -> object
  const reading = normaliseReading(topic, payload);   // topic + payload -> document
  if (!isValidReading(reading)) throw new Error("rejected");
  await readings.insertOne(reading);                  // store in MongoDB
});

6.2 — The backend sends data to the UI. Every 5 seconds the backend reads the latest data back out of MongoDB and pushes a snapshot to the browser over a Server-Sent Events stream (/api/stream):

const payload = {
  readings: await getLatestReadings(),
  sensorTypes: await getSensorTypes(),
  series: await getSeries({ sensorType: "all", minutes: 0, limit: 300 })
};
res.write(`event: snapshot\n`);
res.write(`data: ${JSON.stringify(payload)}\n\n`);

6.3 — The UI receives the values and displays them. Open iot_mqtt_dashboard/client/src/main.jsx. The React app opens an EventSource to the stream and copies each snapshot into React state; React then redraws the cards, chart and table:

const source = new EventSource(`${apiBase}/api/stream`);
source.addEventListener("snapshot", (event) => {
  const payload = JSON.parse(event.data);
  setReadings(payload.readings || []);   // -> the cards and table
  setSeries(payload.series || []);       // -> the chart
});

Trace one reading in your head: the sensor publishes it → the broker delivers it → the backend stores it in MongoDB → the backend streams a snapshot → React shows it. That is the whole pipeline.

Part 7 — Inspect the running system with Ubuntu tools

Now prove the data is really moving, using two standard command-line tools. Keep both programs running and open a third terminal.

7.1 — Read MongoDB directly and see the latest two readings. mongosh is the MongoDB shell. The collection is sensor_readings in the week7_iot database:

mongosh

use week7_iot

// the latest two readings, newest first
db.sensor_readings.find().sort({ receivedAt: -1 }).limit(2)

You should see the two most recently stored documents, each with topic, value, unit and timestamps. Type exit to leave the shell.

7.2 — Watch the broker using the program's own topic. The mosquitto_sub tool (installed with the broker) subscribes from the command line. Use the same topic the program publishes to, so you watch the exact traffic the backend receives:

# watch one sensor's topic
mosquitto_sub -h localhost -t latrobe/building-a/level-2/room-204/temperature -v

# or watch all sensors with the same wildcard the backend uses
mosquitto_sub -h localhost -t "latrobe/+/+/+/+" -v

Every 5 seconds a new JSON message prints. The -v flag prints the topic before each message, so you can see the broker routing by topic in real time. Press Ctrl + C to stop watching.

7.3 — Study how the publisher composes a message. Open iot_sensor_simulator/sensor-publisher.js and read buildPayload. Match each field you see in the mosquitto_sub output to a line here:

function buildPayload(sensor) {
  sequence += 1;
  return {
    deviceId: sensor.deviceId,
    sensorType: sensor.sensorType,
    value: sensor.nextValue(),          // the smooth random-walk value
    unit: sensor.unit,
    observedAt: new Date().toISOString(),
    sequence
  };
}

The object is turned into text with JSON.stringify(payload) and handed to client.publish(topic, message, { qos }). That is exactly the text you saw arrive in mosquitto_sub and get stored in mongosh — the same message at three points in its journey.

Part 8 — Advanced (CSE5006 only)

 

For CSE5006 students

These two extensions modify the front end and then add a new sensor across the whole pipeline. CSE3CWA students are not required to do this part.

8.1 — Change the chart to a scatter plot. The chart is drawn with plain SVG in the LineChart component in iot_mqtt_dashboard/client/src/main.jsx. It currently renders one connected <path> line. To make a scatter plot, render a small <circle> at each point instead of the connecting line. Find the line path element and replace it with:

{points.map((p, i) => (
  <circle
    key={i}
    cx={xFor(times[i])}
    cy={yFor(p.value)}
    r="3.5"
    fill={colour}
  />
))}

Keep the grid lines, axis labels and the last-point marker; only swap the connecting line for the circles. Save the file — Vite hot-reloads it — and the chart becomes a scatter plot. (To keep both, leave the <path> and add the circles as well.)

8.2 — Add a new sensor (water level) end to end. This adds a fourth sensor through the whole pipeline in three small steps.

Step 1 — Publisher. In iot_sensor_simulator/sensor-publisher.js, add a fourth entry to the sensors array:

{
  sensorType: "waterlevel",
  deviceId: `${devicePrefix}-waterlevel-01`,
  unit: "percent",
  intervalMs: 5000,
  nextValue: createSmoothValue({ start: 60, min: 20, max: 95, maxStep: 1.0 })
}

Because the topic is built from sensorType, it will publish to latrobe/building-a/level-2/room-204/waterlevel automatically. Stop the sensor (Ctrl + C) and start it again so Node runs the new code.

Step 2 — Backend. No change is needed. The backend already subscribes to latrobe/+/+/+/+, which matches the new .../waterlevel topic, so it stores and serves the new readings immediately. Confirm with:

curl -s "http://localhost:4100/api/sensor-types"
# -> ["humidity","pressure","temperature","waterlevel"]

This is the payoff of the wildcard subscription: a new sensor type flows through with zero backend changes.

Step 3 — Frontend. The chart is data-driven, so the new type already appears in the Sensor dropdown once it has data. To give it a label, colour and unit (this is the “copy a chart template” step — the same chart now renders the new live series), add one entry to SENSOR_META in main.jsx:

const SENSOR_META = {
  temperature: { label: "Temperature", colour: "#e4572e", unit: "\u00b0C" },
  humidity:    { label: "Humidity",    colour: "#0a8754", unit: "%" },
  pressure:    { label: "Pressure",    colour: "#3066be", unit: "hPa" },
  waterlevel:  { label: "Water level", colour: "#15a0c4", unit: "%" }   // new
};

Save the file (Vite hot-reloads it), refresh the browser, and choose Water level in the Sensor dropdown to see its live chart. You have now added a sensor through the publisher, the broker, the database and the dashboard.

What you should understand after this lab

  • Two independent programs communicate only through the MQTT broker; the broker routes messages by topic.
  • The sensor publishes to a specific topic; the backend subscribes to a wildcard topic filter.
  • The backend takes each packet out of MQTT, validates it, and stores it as a document in MongoDB.
  • The backend reads the latest data back from MongoDB and streams it to the React UI, which displays it without reloading.
  • You can observe the same reading at three stages with standard tools: mosquitto_sub (broker), mongosh (database) and the API endpoint (server).
  • CSE5006: the front end is data-driven SVG, and the wildcard subscription lets a new sensor flow through the whole pipeline with almost no change.
